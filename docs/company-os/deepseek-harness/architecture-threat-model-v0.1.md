## Board architecture rule

**Harness = Execution Substrate**  
**Eyad Company OS = Control Plane**

Eyad Studio retains authority over:

- governance
- policy
- orchestration
- project routing
- QA and independent verification
- browser routing
- project-specific agents
- production approval gates
- plugin allowlists
- kill switch / rollback

## Upstream architecture observations

At the pinned revision:

- Harness is explicitly Developer Preview.
- Cordis provides an everything-is-a-plugin composition model.
- Model adapters, tool registry, session log and agent loop are replaceable through configuration.
- Profiles and bundles compose the runtime as ordered plugin/config layers.
- Session data is event-based and can be persisted independently.
- Subagent providers include in-process and out-of-process options, including Codex and Claude Code integrations.
- Sandbox packages provide same-world process/file confinement, not VM-grade isolation.

## Trust boundaries

### T0 — Company OS control plane

Trusted authority for:

- user intent
- policy
- task dispatch
- approval
- provider selection
- browser routing
- final verification

Harness MUST NOT override T0 policy.

### T1 — Harness runtime

Conditionally trusted execution substrate.

Allowed to:

- run approved agent loops
- dispatch approved tools
- write approved session state
- invoke approved subagents

Not allowed to:

- self-expand privileges
- install arbitrary plugins
- change Company OS policy
- select production secrets
- bypass browser routing

### T2 — Cordis plugins / extensions

Untrusted by default.

Every plugin is treated as executable code and must be version-pinned and reviewed before allowlisting.

Dynamic/model-written packages are **disabled during pilot**.

### T3 — MCP/tool providers

Untrusted by default.

Risks:

- instruction injection
- tool result poisoning
- over-broad file/network access
- hidden side effects
- session contamination

Required controls:

- explicit allowlist
- capability declaration
- scoped credentials
- tool-specific timeouts
- audit log

### T4 — Models and subagents

Untrusted reasoning/execution sources.

Risks:

- policy evasion
- hallucinated capabilities
- unsafe tool calls
- runaway recursion
- cost amplification
- stale/incorrect state propagation

Controls:

- parent-enforced policy
- depth/turn/token budgets
- per-child trace IDs
- kill switch
- independent verifier

### T5 — Sandbox environment

The VM/container is the authoritative security boundary.

Harness-level sandboxing is defense-in-depth only.

### T6 — External browser layer

Browser execution remains an external service boundary:

Company OS
→ Browser Execution Router
→ Jev / Playwright / Browser Agent / Vision

Harness integrates only through an adapter/service seam.

## Primary threat scenarios

### P1 — Malicious or compromised plugin

Potential impact:

- code execution
- file modification
- secret exfiltration
- policy bypass

Mitigation:

- deny-by-default plugin policy
- exact version pin
- dependency review
- disposable sandbox
- no secrets
- no production mounts

### P2 — Dynamic package generated by model

Potential impact:

- arbitrary code execution
- hidden network calls
- dependency compromise

Pilot decision:

**DISABLED.**

### P3 — MCP prompt/tool injection

Potential impact:

- agent follows untrusted instructions
- tool scope expands
- sensitive data is exfiltrated

Mitigation:

- MCP results treated as untrusted data
- Company OS policy precedes tool-provided instructions
- no secret-bearing workloads in pilot
- tool allowlist and verifier

### P4 — Session replay/resume corruption

Potential impact:

- duplicate side effects
- stale state
- incorrect continuation
- cross-session leakage

Mitigation:

- immutable event lineage
- checkpoint verification
- replay tests
- session IDs mapped by Company OS
- idempotency checks for side-effecting tools

### P5 — Subagent failure propagation

Potential impact:

- parent accepts incomplete result
- retry loops
- trace loss

Mitigation:

- explicit child terminal states
- bounded retries
- trace lineage
- parent-side verifier

### P6 — Browser backend leakage into core

Potential impact:

- lock-in
- early fork
- duplicated policy

Mitigation:

- browser adapter contract
- no core modification
- backend selected by Company OS

### P7 — Sandbox escape / host access

Potential impact:

critical.

Mitigation:

- external disposable VM/container
- no Docker socket
- no host home
- no host PID namespace
- deny cloud metadata endpoint
- no SSH agent
- no production mounts

## Architecture acceptance criteria

PASS only if:

1. Company OS can inject/enforce policy without deep fork.
2. Plugins can be explicitly allowlisted and disabled.
3. Browser routing remains external.
4. Session identity can be mapped to Company OS.
5. Trace/audit data is sufficiently complete for independent verification.
6. Runtime can be killed/rolled back without corrupting production systems.
7. All pilot execution remains inside disposable isolation.

Current assessment: **CONDITIONAL PASS FOR PILOT**.
